# SMS4J 渠道调用模式调研报告

> 调研对象：`java/SMS4J/sms4j-provider`（SMS4J 3.3.5）
> 调研目的：为 hioas-sms「配置驱动的 API 调用引擎」提供设计输入
> 调研日期：2026-08-28

## 1. 现有架构

- 统一契约：`SmsBlend` 接口（5 个发送方法 + 异步/延时变体），返回 `SmsResponse{success, data, configId}`
- 每个渠道一个包：`{渠道}/config`（配置类）+ `{渠道}/service`（实现类）+ `{渠道}/utils`（签名工具）
- 公共能力：`AbstractSmsBlend` 提供线程池、延时、重试语义、代理、超时；`SmsHttpUtils` 提供 postJson/postFrom/getUrl 等
- 共 **25 个渠道子包**，全部通过硬编码 Java 构造 HTTP 请求

## 3. 对 Schema 设计的关键输入

1. **Body 格式**：至少需支持 `json`、`form-urlencoded`、`raw`（含 base64 编码）、GET query string
2. **签名**：A 级无需签名；B 级为哈希/编码组合链（md5、sha、hmac、base64、拼接、排序），可用「派生值链 + 函数库」表达；C 级为多步密钥派生 + 规范化请求，同样可分解为哈希/编码原语，但链条较长
3. **共享中间值**：签名中间值常同时出现在多处（助通 tKey、腾讯 timestamp、阿里 nonce），必须支持「命名派生值」且只计算一次
4. **签名依赖请求体**：腾讯/七牛/天翼云的签名包含 body 哈希，引擎必须允许在派生值/请求头中引用「最终序列化后的 body 字符串」
5. **前置请求**：赛邮需先取服务端时间戳，需要 `preRequest` 机制
6. **多操作渠道**：旦米（余额/语音）、赛邮（6 种 action）、助通/鼎众（普通+模板双路由）、极光（验证码校验）需要多 operation + 路由选择
7. **群发策略**：多数为数组/逗号拼接一次提交；布丁云为逐条循环单发 → 需要 `fanout` 策略
8. **特殊响应**：一信通响应为文本（`result=0&` 字符串匹配）；七牛以「error 字段为空」判定成功；华为回执在 `result[0].smsMsgId`
9. **变量序列化差异**：阿里=JSON 字符串、腾讯=数组、云片=`#k#=v&`、网易=两个 JSON 数组字符串、助通=对象数组逐号码展开（`@each` 循环）
10. **无法配置化的渠道**：jdcloud 为纯 SDK，必须保留代码扩展点（SPI 适配器）；unisms 底层可还原为 HTTP，中期可转配置化

## 4. 结论

25 个渠道中，**23 个可用统一的描述文件 + 通用表达式引擎覆盖**（含全部复杂签名，均可分解为哈希/编码/排序原语的组合），**1~2 个（jdcloud，及过渡期的 unisms）需要保留 Java SPI 扩展点**。这决定了 hioas-api 描述标准的三层能力设计：通用模板表达式 → 派生值链 → SPI 兜底。
